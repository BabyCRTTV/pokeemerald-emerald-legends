# Pokémon Emerald: Legends development

The owner may switch models, including Astra and Sol, for different tasks. Use the currently selected model's strengths while preserving the same quality standard, decisions, approvals and project constraints. Maintain a concise, durable handoff so work continues across model or conversation changes.

- Read `docs/DEVELOPMENT-HANDOFF.md` and inspect the live repository before changing anything. Recent commits, PRs, Actions and published files take precedence over older summaries. Root `VERSION` is authoritative.
- Check the connected GitHub tools first and use them for repository writes. A failed web request, clone or container operation does not establish that the connector is unavailable. Check it before asking the owner for files.
- Treat Pokémon Emerald: Legends as a highly interconnected event system. For each intended change, trace only materially related entry conditions, script priorities, shared flags/variables, dialogue, map/warps, quest and achievement triggers, rewards, save/Continue initialization, order-of-completion and retry paths. Identify potential downstream regressions before editing; verify them with focused checks and reliable engine/upstream references as needed. Do not broadly redesign or retest unrelated systems without a causal reason. Prioritize accuracy and quality over speed.
- Attribute every new or materially revised `docs/DEVELOPMENT-HANDOFF.md` entry with a short model/version tagline (for example, `Model: GPT-6 | Reasoning: dependency-focused event review`) plus a concise account of reasoning, changes, related impact and verification/limits. Other models should use their actual identifiers, not copy a predecessor's signature. Keep earlier, unattributed historical entries intact; never retroactively claim another model's work.
- Preserve the owner's Porymap edits, especially maps and tilesets, during routine development, regeneration and releases. The owner may announce small edits; inspect current source and retain them rather than reverting to older generated or approved snapshots. Change these edits only when explicitly requested or when a concrete functional break is verified; then make the smallest necessary repair, preserve the owner's intent and tell them what broke and what changed. Aesthetic differences alone are not a break.
- Preserve approved artwork, existing functionality, native animation geometry and version history. Keep the accepted baseline when making repairs. Publish visual revisions that need approval only after the owner approves those revisions; carry existing authorization forward.
- Preserve older Legends battery saves when releasing updates. This owner requirement supersedes earlier permission to ignore old saves. Review serialized layouts, persistent IDs and initialization; retain legacy readers and add tested migrations before publishing incompatible changes. Follow `docs/SAVE-COMPATIBILITY.md`; reuse the existing fast checks and reserve additional native save/load testing for changes that affect saved data.
- Hoenn, FireRed and Legends variables share the same native array. Before reserving a slot, resolve all direct and symbolic aliases and review reset paths; an unused-looking route name alone is insufficient. Keep an allocation regression for newly reserved slots.
- Use in-game assets for world building and design unless the owner supplies artwork, designs, generations or references for that purpose.
- Match imported metatile backgrounds, edge/corner assemblies and palettes to their actual surroundings. Check the border against neighboring sand, grass, rock, floor and water in game; retain this owner preference during future map design.
- For map and tileset visual work, compare complete vanilla Emerald assemblies with polished ROM-hack references, especially Emerald Crest. Check terrain continuity, vegetation setbacks, stair scale, perspective and material palettes in actual game captures. Preserve the approved visual baseline and use the references to guide coherent composition.
- Use the owner-approved Wyrmtide terrace-depth, stair-fit and whole-exit-rocks galleries as quality references for future in-game edits: complete native silhouettes and bases, matching materials and floor transitions, complete side joins, continuous stair flights, restrained depth lighting and actual movement previews. The approved whole-rock reference is `docs/designs/wyrmtide/whole-exit-rocks/README.md`. Preserve the approved source; apply these lessons to new work without regenerating owner maps.
- Convey height with coherent upper rims, shaded vertical faces and fitted contact shadows while preserving accepted terrain geometry. Use actual movement captures when still images leave up/down travel ambiguous.
- For wider stair flights, assemble continuous native treads with outer edges once and matching floor/rock landings; repeating complete narrow flights introduces duplicate rails. Inspect both neighboring rock end-cap pairs as well as ordinary/wide tread continuity, and verify physical stair approaches in game.
- Use complete native silhouettes and bases for freestanding rocks. Do not crop a wall end-cap into a standalone rock; inspect the full outline against surrounding floor in game.
- For widened warp entrances, make every visible walking lane functional. Preserve existing warp indices, append aliases where needed and test entry/return on both sides in game.
- For private field palettes, verify the engine's loaded bank range and actual per-map tile usage; an unused atlas bank is not necessarily loaded. Preserve native day/night palette wiring and confirm distinct shades after RGB555 conversion in actual animated captures.
- Verify canonical Git blob hashes when transporting binary layouts and tilesets. A base64 wrapper can conceal text transcoding; prefer raw Git bytes and reject a mismatched byte count/hash before editing.
- Prefer previews from the actual game compositor for existing sprite work. Distinguish sprite-buffer previews from emulator captures and retain exact pixels when scaling.
- For **gameplay previews**, use only frames captured from the actual compiled Pokémon Emerald: Legends ROM running in mGBA or another verified emulator. Do not use stock Emerald images, unrelated game screenshots or AI-generated stand-ins; distinguish sprite-preview compositions from genuine emulator images and label the ROM version and capture source.
- For routine route/seasonal encounter additions, do not generate or present user-facing DexNav preview sheets or wait for preview approval when the approved art/UI is unchanged. Continue appropriate build/native/regression checks, using internal captures where useful, and synchronize wiki/LegendsDex rosters, seasons, times, levels and odds with each verified shipped release.
- Run focused mGBA gameplay tests where feasible, not just native compilation. The native mGBA Quickstart smoke is an additional release gate, but it alone does not verify changed dialogues, events or old battery saves. Test affected interactions in the emulator and disclose untested scenarios rather than imply they passed.
- Reserve space for new reminders and HUD elements; verify screen rectangles and physical tile allocations, and remove them before competing menus/dialogs.
- Validate relevant changes and regressions. Verify native Release and Debug builds and independently apply both BPS patches against the supported clean Emerald base before claiming readiness. Confirm commits, merges, Actions results and live downloads before reporting them as completed.
- Keep versioning, all three changelogs, Options, README, site and browser patcher consistent. Preserve Release/Debug distinctions.
- When advancing the wiki encounter source pin, synchronize the source-keyed atlas/profile script URLs with the no-store JSON and run the reader regression. Stale script metadata can make the sprite preload guard reject otherwise unchanged approved art.
- Write changelog entries in past tense so readers can easily distinguish completed changes from planned work. Apply this convention to all three changelog files and the website changelog.
- Update the handoff with accepted decisions, approval state, commit/build evidence and outstanding work at each completed milestone or interruption. Keep it short, and store detailed evidence in linked QA records. Avoid dumping full logs, registries, binary data or repeated inspections into the conversation.

- Review this file at each release; update it when a durable owner preference or workflow rule changes. Keep version-specific approvals, commits and evidence in `docs/DEVELOPMENT-HANDOFF.md` and linked QA receipts.
