## Behavior and trust boundary

- New `pages.yml` responds to master docs/publishing changes and completion of the existing project, shared native/patch, wiki, Android and Windows workflows. PRs run read-only fixture validation. Production always checks out current master, never the triggering PR or its artifact; only the final deployment job receives Pages/OIDC write permissions.
- Gate matching reads current workflow path filters and compares actual tracked Git blobs against successful master-push runs in master ancestry. The newest matching attempt governs: failure, cancellation or incomplete execution retains the current site. Workflow changes invalidate that workflow's prior evidence. Bot-managed download/version outputs are excluded; only explicit handoff/process/QA text is excluded from host input matching. Unsupported path-filter forms fail closed. Searches stop after three pages of 100 runs; old/expired evidence needs fresh production verification.
- The successful production shared-build artifact supplies the five-file patch payload. GitHub's archive SHA256, exact file allowlist, canonical-base identity, twelve named native receipts, native ROM target identities, decoder receipt and BPS CRCs are checked. No ROM/ELF/save is uploaded. Current committed downloads must be byte-identical to those verified BPS files and checksums. No new Legends compilation is introduced by this Pages workflow.
- Before staging, reject symlinks and ROM/ELF/save files. Check the home label/links, browser patcher version, changelog header, LegendsDex game version and APK/manifest hash. The changelog's stale v0.0.72 header/description was corrected to the existing v0.0.75 entries; this is a publishing-label repair, with no artwork or game change.
- Copy the complete site into a private partial directory, produce an exact every-file manifest and critical-file HTTP expectations, then rename the complete directory into place. Interrupted staging removes partial output. A deterministic `release-publication.json` records source, gates, patch provenance and every staged asset. Only that full Pages artifact can deploy.
- A single production concurrency group serializes promotions without cancelling an in-flight deployment. Current master and each evidence run's attempt/status are checked again immediately before deployment. Superseded staging holds for a newer event. The complete existing live snapshot remains until successful promotion. The actual critical live files, manifests, both patches and BPS CRCs are verified after deployment. An already identical, successfully verified snapshot avoids another deployment.

## Limits

The transaction boundary is one complete Pages artifact, not all clients' already cached files, GitHub Release assets or uninterrupted external network availability. Existing Windows installer clobber behavior, Android signing requirements and companion content-triggered rebuild policy are preserved. Current-pair BPS cleanup remains unchanged: the old live pair stays available during staging, but old URLs are not promised after a new version promotes. Gate status and master are checked immediately before the deployment request; a subsequent source push can only be reflected by its later coherent deployment, not a cross-service compare-and-swap. Fixtures test interrupted staging/retry and stale evidence; a deliberately failed real production deployment or concurrently raced release has not been performed. Existing native/owner-save/Pizza Boy/full-story limits remain.
